# Aragorn — Stage 5 Notification Scope Decisions

**Date:** 2026-08-13T21:27:04-03:00  
**By:** Aragorn  
**Stage:** 5 — Power Automate Notifications

---

## Decision 1 — Trigger Mechanism: HTTP Push (confirmed)

**Chosen:** HTTP trigger — our .NET `TravelRequestService` calls each Power Automate "When an HTTP request is received" flow URL immediately after each state transition commits to the database, posting a JSON payload with all context the flow needs.

**Rejected:** SQL connector polling trigger. Reasons: (a) requires a premium SQL connector and often an on-prem data gateway even for Azure SQL polling, (b) introduces polling delay vs. true push, (c) Power Automate would need to re-query Employee/Manager details it doesn't have — violating Sam's charter principle of not duplicating business logic inside flows.

**Rationale:** Our code already holds Employee.Email, Manager.Email, Destination, Dates, Status, Comments at the moment of the transition. Push the context in one call; Power Automate's job is email delivery only.

---

## Decision 2 — Two Flows (confirmed)

**Chosen:** Two separate HTTP-triggered flows:
- **Flow A — "New Request Submitted":** Triggered on Submit *and* Resubmit (same payload shape, same URL). Sends email to the assigned Manager.
- **Flow B — "Request Status Changed":** Triggered on Approve, Reject, and Return. Sends email to the Employee.

**Rejected:** Single flow with Switch on EventType — more complex to build and debug in the Power Automate designer for no significant gain at this scale.

**Rationale:** The two-flow design maps 1:1 to the two notification audiences (Manager and Employee). Each flow is independently testable. Resubmit reuses Flow A because the audience (Manager) and context (same ApproverId = Employee.SuperiorId) are identical.

---

## Decision 3 — Recipient Emails Resolved by .NET (confirmed)

**Chosen:** The HTTP payload includes `EmployeeEmail` and `ManagerEmail` as resolved string fields, computed by .NET from `Employee.Email` and the approver's `Employee.Email` at transition time.

**Rejected:** Power Automate performing its own DB/Dataverse lookup to resolve emails from an ID.

**Rationale:** Power Automate flows remain simple (no secondary lookups, no SQL connector needed inside the flow). The .NET layer already has the full `Employee` graph loaded when it processes each transition.

---

## Decision 4 — INotificationService in TravelRequestService (confirmed)

**Chosen:** Introduce `INotificationService` interface + `PowerAutomateNotificationService` implementation in `TravelRequestWF.Infrastructure/Services/`. Injected into `TravelRequestService` via constructor DI. Responsible for the `HttpClient` calls to Flow A and Flow B URLs.

- `Submit` → calls Flow A
- `Resubmit` → calls Flow A (same payload shape, same URL)
- `Approve` → calls Flow B
- `Reject` → calls Flow B
- `Return` → calls Flow B

**Rejected:** Inline `HttpClient` usage scattered inside `TravelRequestService` methods.

**Rationale:** Keeps `TravelRequestService` focused on state transitions. `INotificationService` is swappable (stub for tests, real HTTP for production). Follows existing `BlobStorageService` precedent.

---

## Decision 5 — Non-Blocking Notifications (confirmed)

**Chosen:** Notification HTTP calls are **best-effort**. Failures are caught in a `try/catch` inside `PowerAutomateNotificationService`, logged via `ILogger<PowerAutomateNotificationService>`, and do **not** throw or roll back the database transaction. The transition succeeds regardless of notification outcome.

Additionally: if the configured URL is still the placeholder value (e.g. starts with `"PLACEHOLDER"` or is empty/null), the service skips the call and logs an informational message — no error, no throw.

**Rationale:** Notifications inform; they do not govern. A failed email must never block an employee's request approval. Matches the "Power Automate is the notification bus, not the workflow engine" decision from prior stages. Avoids the anti-pattern of external dependency blocking core workflow (lesson from Stage 4 review).

**Chosen:**

  - `PowerAutomate:FlowBStatusChangeUrl` (placeholder value: `"PLACEHOLDER_FLOW_B_URL"`)

## JSON Payload Contract (canonical reference)

Both flows receive HTTP POST with `Content-Type: application/json`.

### Flow A Payload (Submit / Resubmit → Manager notification)

```json
{
  "RequestId": "guid-string",
  "EventType": "Submitted",
  "EmployeeName": "string",
  "EmployeeEmail": "string",
  "ManagerName": "string",
  "ManagerEmail": "string",
  "Destination": "string",
  "StartDate": "2026-08-20",
  "EndDate": "2026-08-25",
  "Purpose": "string",
  "Status": "Pending",
  "Comments": "string or null"
}
```

`EventType` values for Flow A: `"Submitted"` or `"Resubmitted"`.

### Flow B Payload (Approve / Reject / Return → Employee notification)

```json
{
  "RequestId": "guid-string",
  "EventType": "Approved",
  "EmployeeName": "string",
  "EmployeeEmail": "string",
  "ManagerName": "string",
  "ManagerEmail": "string",
  "Destination": "string",
  "StartDate": "2026-08-20",
  "EndDate": "2026-08-25",
  "Purpose": "string",
  "Status": "Approved",
  "Comments": "string or null"
}
```

`EventType` values for Flow B: `"Approved"`, `"Rejected"`, or `"Returned"`.

`StartDate` and `EndDate` are ISO 8601 date strings (`yyyy-MM-dd`).  
`Comments` may be `null` — Power Automate should coalesce to an empty string in email body.

## Summary

| # | Decision | Choice |
|---|---|---|
| 1 | Trigger | HTTP push from .NET |
| 2 | Flow count | Two flows (A: Manager, B: Employee) |
| 3 | Email resolution | .NET resolves emails in payload |

| 5 | Failure behavior | Non-blocking — log, don't throw |
